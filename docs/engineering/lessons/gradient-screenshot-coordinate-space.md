# 渐变截图的坐标空间

## 症状

微信框架 IDE 的 12 项验收通过后，#928 渐变对照在截图尺寸断言失败：旧基线为 449×238，当前裁剪为 392×208。两张截图的四组渐变形状及颜色一致，但像素密度不同。

## 根因与纠正

测试用运行时节点坐标乘截图缩放比例，再直接与历史物理像素基线比较。DevTools 返回 640 像素宽截图，运行时视口为 390 CSS 像素，不能假设截图密度与旧环境相同。

改为从运行时 CSS 坐标区域采样，输出一 CSS 像素对应一图像像素的对照图。三个定位节点的并集加 2 CSS 像素边距为 240×128，节点仍为 112×56。归一化不读取旧基线尺寸，因此真实布局宽高改变仍会触发尺寸断言。保留原像素比较阈值和颜色、结构断言，未放宽验收标准。

将图像、渐变和坐标处理从超过 600 行的测试拆到 `e2e/issue-928/`。两个场景已经消费同一 v4 项目，合并为一次构建和一次自动化连接，避免迁移后遗留的重复启动；仍分别切页验证。

## 验证

- `pnpm exec vitest run -c e2e/vitest.e2e.config.ts e2e/issue-928-css-pixel-region.test.ts --update=none`：5 项通过，覆盖 1.5/2/3 倍截图密度、真实尺寸变化和区域越界。
- 仅执行 `E2E_UPDATE_ISSUE_928_BASELINE=1 pnpm e2e:ide:issues-909-916-928` 更新 v4 渐变对照图。首个场景通过，原独立的第二套件在重复启动时超时，保留原报告。
- 复用连接后取消更新变量运行 `pnpm e2e:ide:issues-909-916-928`：两项真实 IDE 测试通过、无跳过，约 33 秒。
- 上述 IDE 命令显式使用本轮官方 CLI。原图、旧基线和更新前尺寸证据保存于 `e2e/.artifacts/preflight/32ad0e2f-43fb-4b7a-85f5-f4a739fd1466/issue-928-before/`，定向更新和不更新验证日志在同一 run 目录。

## 适用边界

坐标归一化只消除截图密度差异，不掩盖布局变化、缺失区域或颜色差异。不同渲染器引起的真实像素差异仍须逐项调查，不能通过缩放到旧基线任意宽高绕过。

后续真实截图发现非整数缩放下，原视口已经含有向外取整与宿主缩放造成的位置偏差。仅归一化 CSS 尺寸不能恢复这些坐标信息；像素基线新增整数采样比例约束并校准，详见[微信截图缩放与渐变基线](wechat-screenshot-pixel-alignment.md)。本记录的历史通过不代表任意缩放下像素等价。

## 规则评估

不新增 AGENTS 规则。沿用既有截图几何、结构探针和基线需解释的约束，通过独立回归固定坐标空间。
