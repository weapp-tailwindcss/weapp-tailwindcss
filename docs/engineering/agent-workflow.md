# AI 协作与证据闭环

## 接单与隔离

读取根规则、目标目录的全部适用规则和任务明确指定的技能。版本以 manifest 为准，脚本先确认存在；占位命令不是可直接执行的验证。修改任务使用独立 worktree，记录基线 SHA、分支、已有改动和进程所有权。执行前后检查状态，不清理不属于自己的改动。

## 事实与复现

先读取 Issue 最新评论及其截图，把用户操作变成可观察的验收条件。记录框架、平台、命令、依赖实际解析路径和编译器版本。明确区分已观察事实、待证假设和环境阻塞。

测试预期必须来自项目配置和产品语义，不照搬默认 theme 数值。组件属性必须有真实消费方。首次加载先建立基线，再验证增量。Web 验证须确认服务根目录身份、端口和当前构建，不能仅凭标题或 localhost URL 判断实例。

## 根因与回归

沿输入、转换、产物、运行时逐层找首次偏离。先固化失败用例，再修改负责该行为的模块；用相同用例验证修复前失败和修复后通过。未复现时不制造产品补丁，也不凭 mock 单测宣称用户环境已修复。

HMR 在同一服务进程连续修改，覆盖新增、替换、删除和最终浏览器刷新。保存标识与被测属性尽量在一次写入提交；等待本轮 DOM、CSS 和计算样式一致，不用旧 marker 或固定等待证明成功。保留服务端错误、请求失败、页面日志和失败截图。

## 全面依赖升级

用户要求“全面升级”或“升级全部依赖”时，按以下流程执行。通用更新入口的成功只证明该入口处理过的范围，不能作为全仓完成凭据。

### 清单与版本通道

1. 按 `pnpm-workspace.yaml` 与 `templates.jsonc` 盘点根项目、全部 workspace 项目、全部 demo（含 Web、issue 复现与 style-injector）及独立模板，排除 `node_modules`、构建输出与其他生成产物。通过依赖声明和实际构建配置识别框架，不依赖目录名称；逐项记录项目、依赖、当前声明与实际解析版本、目标版本、升级方式和结果。
2. 默认选择上游正式版，以官方发布通道判定，不仅凭版本字符串中的连字符判断是否为预发布；核对 Node/pnpm engines、peer 与框架配套约束。只有必要能力尚无正式版时才保留 alpha，并记录官方依据、完整工具链版本和退出例外条件。uni-app-x 不自动成为 alpha 例外。专门覆盖旧版本兼容性的样例保留测试目的，逐项说明保留版本及复查条件，不静默抹去回归场景。
3. 普通依赖沿用 `pnpm up:pkg`、`pnpm up:pkg:latest` 等现有入口；这些命令及 `update.ignoreDeps` 排除的框架依赖进入专项升级清单，不能视为已处理。uni-app 项目中的组件库、图标、Sass 等非编译器依赖也须检查。独立模板按[模板依赖升级流程](template-dependency-upgrade.md)处理，并纳入总清单。

### uni-app 与 HBuilderX 工具链

uni-app CLI 编译器使用官方 `@dcloudio/uvm` 获取配套版本。每轮先查询并固定当轮工具版本，核对其参数与行为；2026-10-28 核实的版本为 `0.3.1`。在每个目标项目目录运行以下正式版预览命令，不在仓库根目录代替各项目执行：

```sh
pnpm dlx @dcloudio/uvm@0.3.1 latest --manager manual
```

`latest`、`alpha` 与指定编译器版本均为位置参数；`0.3.1` 不支持 `--latest`、`--alpha` 或 `--dry-run`，也不能用 `--version` 查询工具版本，因为它可能按默认目标开始升级。`manual` 只输出配套清单，不安装或改写目标项目依赖，其输出不视为稳定 JSON 接口；`pnpm dlx` 自身仍会获取工具及其依赖。

审查 UVM 清单与实际编译器约束后，同步各项目 manifest 及已有 catalog，保留 `workspace:`/`catalog:` 关系，在仓库根目录统一执行 `pnpm install`；独立模板维护各自锁文件。UVM 的 pnpm 安装模式必须显式选择 `--manager pnpm`，但本仓库默认采用上述 manual 流程，避免直接安装改写 catalog 引用。不能把所有 `@dcloudio/*` 机械设置为相同版本或 npm `latest`。

UVM 只增加或更新编译器主要配套依赖，可能新增平台包并调整 Vue/Vite 等依赖，不保证覆盖全部 DCloud 包，也不会补齐构建 scripts。逐项核对新增平台包、未覆盖的 DCloud 包、Vue/Vite 配套与目标平台构建脚本；版本模板回退不能代替实际编译器约束验证。UVM `0.3.1` 未将安装子进程的非零退出码作为失败传播，不能仅凭 UVM 退出成功判定升级完成。

HBuilderX 与 uni-app-x 按实际构建入口分别登记项目 npm 编译器、IDE、内置编译器和运行基座版本，按对应正式工具链整体对齐。UVM 不升级 HBuilderX 内置编译器、原生 SDK 或运行基座；项目 npm 依赖已更新不代表 IDE 链路已更新，也不能混用 IDE 与 npm 编译器作为验证兜底。

官方依据：[DCloud 编译器版本管理](https://uniapp.dcloud.net.cn/quickstart-cli.html#cliversion)、[UVM 参数入口](https://unpkg.com/@dcloudio/uvm@0.3.1/bin/index.js)、[UVM 安装实现](https://unpkg.com/@dcloudio/uvm@0.3.1/lib/project.js)、[uni-app-x 工具链兼容说明](https://doc.dcloud.net.cn/uni-app-x/tutorial/compatibility.html)。上游工具或框架支持变化时重新核实这些约束，不沿用旧版本结论。

### 验证与交付

- 核对 manifests、共享 catalog、根与独立模板锁文件、overrides、精确版本补丁及实际安装版本；共享配置变化须追踪到全部受影响项目，不能因项目未被通用命令选中而跳过。Node/pnpm 声明与项目工具链也纳入兼容性核对；不手工改写生成的锁文件。
- 安装更新后完成 `pnpm install --frozen-lockfile`、受影响构建与对应回归，独立模板在各自目录验证。demo 工具链或依赖变化后，定向重新生成 static 基线、审查语义差异，再以禁止更新模式复验；产物无差异也记录项目、命令与结果。涉及 HMR、IDE、原生基座时验证对应真实链路；本地全面验收仍须先通过下述全端预检，不得以单次构建替代。
- 逐项交付“已升级、已是最新、保留、阻塞”清单，保留项说明兼容性或复现场景依据及复查条件；另列验证的通过、失败、跳过和阻塞范围。存在未处理项目或未完成验收时明确报告剩余范围，不能以通用入口、UVM 退出码或历史报告宣称全面完成。
- 规范自身的文档变更运行 `pnpm agents:check` 和 `git diff --check`，核对链接与命令，不因此执行实际依赖升级或全端测试。

## 全面测试环境门禁

用户要求全面、本地全端或全仓验收时，先执行环境预检，再启动任何全面测试的构建、单测或 E2E 阶段。手动拆分命令同样受此约束，不得通过改为单端或 smoke 名义绕过用户要求的全面验收。

按[多端手册](../../e2e/LOCAL-MULTI-PLATFORM-E2E.md)完成 prepare、当前 AI 会话的 computer use 证据和 verify，将本轮报告传给全面测试入口。仅有进程、版本输出或历史截图不代表就绪；脚本探针和 AI 工具证据缺一不可。全面入口领取报告后固定设备与 IDE 实例，在进入设备阶段前再次检查。

允许安全启动已安装且目标明确的工具。认证、登录、权限、安装、目标歧义和用户会话冲突应阻断，不能通过关闭用户程序、重置设备或修改验收门槛解决。工具调用失败时立即在当前对话说明失败项、原始错误、已经尝试的安全启动、未执行范围、报告路径和用户需要的恢复动作。仅继续有界诊断与本任务清理，不继续后续测试。

中断恢复、设备或 IDE 切换、源码/checkout 改变后重新 prepare。旧报告不复用；在工具链失败后不得宣称产品测试通过。定向单测和预检实现回归可独立执行，普通 hosted CI 的健康检查不是本地全端通行证。

## 分层验收

1. 定向单测与真实解析器/编译器集成测试。
2. 受影响包构建、类型与回归，确认使用当前 worktree 的依赖和构建产物。
3. 对应 demo 的 static 基线和真实运行链路；设备流程见 [多端手册](../../e2e/LOCAL-MULTI-PLATFORM-E2E.md)。
4. 检查 diff 与规则：`git diff --check`、`pnpm agents:check`。

正常测试设置 `CI=1`；Vitest 5 显式使用 `--update=none`，禁止使用会被解释为更新参数的 `--update=false`。E2E 配置同时默认 `update: 'none'`，显式 `-u` 才更新基线。更新基线必须单独执行、限定项目、说明语义差异，再运行不更新的验证。聚合构建的缓存命中、跳过目标、测试 skip 均单独报告。

## 性能优化与语义边界

优化前先固定行为不变量和真实失败回归，再测热点。优先减少重复解析、分配、索引构建和大数组移动；fast path 的条件必须能证明被跳过的处理没有语义贡献。覆盖空输入、混合来源、重复覆盖、大输入及 legacy/graph；不得按文件大小跳过必要处理。

微基准记录输入规模、预热、采样次数和统计方式，再以相同配置的真实框架构建/HMR 验证耗时和峰值内存。单次阈值附近失败不足以证明性能退化，也不足以归因为环境噪声：保留首次样本及重试结果，在同一 SHA、配置下有限复测；重复失败应定位热点，禁止反复重跑直到偶然通过或放宽阈值。

## 远端 CI 跟进

仅在任务已要求远端验收时执行长时间跟进。记录 PR head SHA、run ID、attempt 与失败 job；PR 更新后重新核对测试提交，旧 head 的成功不能证明新 head。远端分支被推进时先检查归属和 diff，在独立 worktree 整合，不覆盖外部提交。

按失败日志区分代码、基线语义、基础设施和待证性能波动，再选择修复或有限重试。取消旧 run 前检查 concurrency group、被调用工作流和依赖关系；不要误取消当前 head 的任务。只重跑确认需要重试的失败集合，不重复触发已成功的全矩阵。

使用可中断、单次不超过 60 秒的等待，按任务时长控制 API 查询频率；状态不变时减少查询和重复进度消息，约定只汇报新失败、重要阶段完成或需要用户行动的变化。查询超时不代表任务终止，应复查同一 run；排队仍在推进时不要重启或宣称阻塞。不要把队列等待时间计为编译性能。

完成前重新查询当前 head 的全部检查，分别列出成功、失败、跳过、取消和未完成；检查 required gate 的依赖及跳过条件。无失败但仍排队不算通过，按条件跳过也不能写成已执行。交付包含最终 SHA、run 链接和本次本地验证范围。

## 提交与上游修复

修复交付前逐项核对实际 diff 中的负责模块、持久回归、受影响基线、中文 change intent 和验证记录。可拆成多个提交，但用户要求的交付集合必须完整；测试运行日志不能替代测试文件。公开包行为变化通过 `pnpm release status` 确认 intent 和实际消费包范围；纯工程文档不触发无关包版本提升。

第三方缺陷先核对实际实现包及上游已有 Issue/PR，在已有授权范围内提交最小复现、回归和修复。临时依赖 patch 需要记录精确版本、上游链接、验证范围及移除条件；上游版本可用后检查修复覆盖，升级并删除对应 patch/锁文件登记，不能只留下长期临时补丁。

发布部分成功时逐项对账 npm 版本、tag、目标提交与 GitHub Release。恢复应先 dry-run，只补缺失元数据；请求发送和响应体读取都属于可失败边界，POST 结果未知时先查询确认。禁止通过外层重试整个 npm publish 处理 Release API 故障。实际发布仍遵循根规则与用户授权。

本流程的案例与边界见 [CSS、性能与 Release 修复复盘](lessons/ci-css-release-recovery.md)。

## 沉淀与自我修正

根因修复、错误结论纠正或可复用的流程失败，需要在 `docs/engineering/lessons/` 留一份中文记录，链接持久回归和证据。原始大日志放到忽略的 artifacts；记录保留关键错误、命令、结果和适用版本，不能只留本机路径。

记录使用 YAML frontmatter：`status` 为 `verified`、`partial` 或 `superseded`；`issue` 为来源 URL；`baseline` 为原排查基线的完整提交 SHA；`regressions` 为仓库相对测试路径数组。正文包含“症状”“根因与纠正”“验证”“适用边界”“规则评估”。

新建或更新复盘时，可使用 `verification` 数组记录各项结论的验证来源；未使用该字段的历史记录继续兼容。提供时必须为非空数组，每条只允许以下字段：

| 字段 | 约定 |
| --- | --- |
| `claim` | 非空字符串，说明该项验证支持的具体结论 |
| `kind` | `unit`、`integration`、`ci` 或 `native` |
| `status` | `passed`、`failed` 或 `pending`；跳过的验收记录为 `pending`，在原因中说明 |
| `sha` | 被测或待测的完整 40 位十六进制提交 SHA |
| `environment` | 非空字符串，记录实际或目标系统及 Node/IDE 等版本 |
| `command` / `url` | 已执行记录至少提供一个；命令为非空字符串，URL 为完整 HTTPS 地址；提供的字段均须有效 |
| `reason` | 待验收记录必须说明原因；提供时必须是非空字符串 |

`baseline` 保留原排查基线，各条 `verification.sha` 记录实际验证提交。包含未提交改动时在环境和正文中说明，不把原始 SHA 当作包含修复的源码。单项通过不改变整篇 `partial` 状态，也不证明全部环境或根因已经解决。

每次交付评估规则变化：优先修正已有条目或补可执行测试；只有跨任务可复用且有证据的约束才进入 AGENTS。允许说明“不新增规则”。推翻旧结论时保留原因和替代记录；过时经验标记 superseded，不静默覆盖历史证据。

根规则只放跨仓库硬约束，领域规则只放局部差异，操作步骤只有一个权威文档。新增规则须给出触发场景、验证入口和复查条件；不以重复或更长的规则代表更高质量。

## 自动检查与边界

`pnpm agents:check` 是只读检查，验证规则索引、相对文件链接、明确 pnpm 命令、复盘引用及可选证据字段的结构；证据错误包含文件和从 1 开始的 `verification[n]` 位置。它保持离线，不查询远端、不执行文档里的命令、不改规则或更新快照，也不判断证据真实性、因果关系或语义正确性，不能把 CI 通过换算为原生验收通过。新增语法或规则变更先补检查器测试。

纯 Markdown PR 同样执行独立规则检查。AI 可以在授权任务中提出和实现有证据的规则修订，但不得自行放宽安全边界、操作用户会话、发布、关闭 Issue 或创建后台任务。

交付必须分列通过、失败、跳过和阻塞，列出尚未验证的环境，以及本次是否更新了规则和原因。
